### What exists, end to end

sources (10 adapters) -> ingest with content-hash gate -> canonical jobs -> LLM extraction
(validated, repair loop) -> index (full text and 768-dimension embeddings) -> hybrid search API
-> profiles -> matching on a task queue (job side and profile side) -> stored, idempotent
matches -> `MatchNotifier` hook -> live feed (phase 7): the worker (and `python -m sanket.matching
--inline`) publish each new match to a Redis channel per profile when `REDIS_URL` is set
(`RedisMatchNotifier`, built by `registry_from_settings`; no-op without Redis), and
`GET /profiles/{id}/matches/stream` sends the stored row as a Server-Sent Event with the match id
as the event id, resumes from `Last-Event-ID`, and catches up from the database when idle.
`backend/tests/e2e` runs the chain with recorded payloads and fakes, including the feed on a
fake Redis and the whole API behind real authentication.

Around the pipeline (phase 8):

- **Authentication.** Every route except `/healthz` and `/readyz` needs `Authorization: Bearer`
  with an HS256 or JWKS-verified JWT or a static API key; the subject (or the key's owner) is the
  owner id and scopes every profile, match and stream query (another owner's id is a 404).
  `GET /search` needs a credential unless `SEARCH_PUBLIC=true`. A browser `EventSource` uses
  `POST /auth/stream-token` and `?stream_token=`: a one-minute token bound to one owner and one
  stream path (ADR 0008). `AUTH_DEV_BYPASS=true` is allowed in development and test and refused
  in production: with `ENVIRONMENT=production` the settings do not load, so no process starts (ADR
  0008 amendment); the API also refuses to start with no authentication configured.
- **Errors, logs, limits.** One JSON error envelope with a request id (also in `X-Request-ID` and
  every log line); redacted JSON logs; per-owner (else per-address) rate limits, in Redis when
  `REDIS_URL` is set and in memory otherwise, with streams exempt (ADR 0009).
- **Operations.** `/healthz` (liveness), `/readyz` (database, Redis, migrations), `/metrics`
  (Prometheus, own token), optional OpenTelemetry tracing, alert rules and a Grafana dashboard
  under `ops/observability/` (ADR 0010). Worker liveness and task counters are on `/metrics` too,
  from a Redis heartbeat and counters (ADR 0011, pre-deploy hardening).
- **Compose.** `docker compose up -d --build api worker` runs `db`, `redis`, a one-shot
  `migrate`, then `api` and `worker` with health checks (the worker's is its Redis heartbeat), a
  non-root read-only image and ports on loopback; `--profile observability` adds Prometheus, Grafana and an OpenTelemetry collector;
  `--profile jobs run --rm ingest` runs ingestion. `docs/deploy.md` has the settings and
  `docs/runbook.md` the release order, rollback, queue, alerts and secret rotation.

## Bugs found and fixed

Found by tests, by reading, or against local data while building. Each fix is in the commit
named.

- Ingest marked a whole source failed when one Remote OK or Remotive item was malformed
  (`65a39c6`).
- Re-ingesting a changed posting kept its old title and description under the new hash, so
  extraction could record stale text as current (`56b7834`).
- A posting that changed during the model call could still get its result stored on first
  insert; the stale-write guard only covered updates (`a1fcf0e`).
- Prompt injection through the posting wrapper tag: look-alike and disguised forms of
  `</posting>`, and fused block text, are neutralised (`389d129`, `164e5cd`; PROMPT_VERSION
  went from 2 to 3 once, so existing postings become pending for re-extraction).
- The backfill had no converters for `jobtech_se` and `usajobs`, and nothing failed when a new
  source lacked one; now a test does (`9233c5c`).
- JobTech salary text carried a pay-type label (`cd107d0`).
- A location that was only the word "Hybrid" was treated as no location, merging unrelated
  Cloudflare postings into one job (`291c3b1`).
- Two workers racing on a first match could both announce it; first matches are now inserted
  with ON CONFLICT DO NOTHING so only one announces (`25e0b8b`).
- The live feed leaked a Redis subscription on every client disconnect: the server cancels a
  streaming response with a scope that cancels again at each await, so the cleanup was
  abandoned half way. Found by running against a real Redis and uvicorn; fixed with a shielded,
  time-bounded close and a test that cancels the same way (`27fe278`).
- Redis pub/sub does not redeliver a lost message, so an idle stream now catches up from the
  database instead of waiting for the next event (`660d3e1`, an addition after the first
  version rather than a reported failure).
- Adding authentication and the error envelope changed what the existing API tests could
  assume (requests acted as the default owner, error bodies had another shape); the tests were
  updated in phase 8, and the end-to-end tests use the development bypass except where a test is
  about authentication (phase 9).
- A trap rather than a defect: `TestClient` never sees the end of a stream, so a test that opens
  the real feed route through it hangs unless `FEED_MAX_STREAM_SECONDS` is tiny. The end-to-end
  tests read live streams with a streaming ASGI client (`backend/tests/e2e/sse.py`) and use
  `TestClient` only for answers that end at once (401, 404, 429); run a new stream test under a
  hard timeout the first time.
- The smoke check could not open the stream once the API required credentials and the browser
  flow needed a stream token; it now mints one and falls back to the bearer header (phase 9).

## Risks and limits

- **Company names from board slugs.** Lever and Ashby (and Greenhouse when the list response has
  no company name) use the board slug as the company, so their jobs rarely fingerprint the same
  as the same job on an aggregator that uses the real company name. Cross-source grouping and
  matching will often miss these; the cheaper error was chosen on purpose (ADR 0002).
- **`notified_at` means "the publish was accepted".** The worker and the matching commands use
  the Redis notifier when `REDIS_URL` is set (checked in `registry_from_settings` and the
  matching CLI), so `notified_at` is set when `PUBLISH` returned, also when nobody was listening;
  the row is the source of truth and a stream that connects later replays it. Without
  `REDIS_URL` the notifier is the no-op one and `notified_at` is still set with nothing
  published, so a deployment must set `REDIS_URL` on the worker to have a feed at all.
- **One Redis connection per open stream** (capped at 200 streams per API process and 5 per
  profile), outside the connection pool. Delivery is at least once: clients must ignore an id
  they have seen. A match withdrawn and reactivated keeps its id, so a client already past it is
  not replayed it. There are no match or notification counters in the metrics (ADR 0010).
- **Rate limits and metrics are per API process.** Without `REDIS_URL` several API processes
  multiply the effective limit, and Prometheus must scrape every process and sum. A proxy or
  firewall limit in front is still advisable: the limiter protects the API, not the host.
- **`TRUSTED_PROXY_HOPS` must match the real proxy setup.** Too low and every caller shares the
  proxy's address (one budget for all unauthenticated traffic); too high and a caller can forge
  its address through `X-Forwarded-For`.
- **The worker has no tracing.** Its liveness and task counters are exported through the API's
  `/metrics` (heartbeat and counters in Redis, ADR 0011), but it has no spans of its own, and
  request ids are not carried into queued tasks. The heartbeat shows the process is alive and
  reaches Redis, not that a task is progressing: a stuck task is bounded by the task timeout, and
  a worker that is alive but not consuming shows as queue age. A missing worker does not make the
  API unready (by design); the `SanketWorkerDown` alert is the signal, and Compose does not
  restart a container that is merely `unhealthy`.
- **No database spans.** The SQLAlchemy OpenTelemetry instrumentation does not support SQLAlchemy
  2.1 yet, so tracing shows HTTP spans only until a release that does is installed (ADR 0010).
- **JWKS is tested only with a fake key source**, never against a real identity provider; test
  that integration, and the issuer, audience and owner-claim settings, before relying on it.
  Tokens cannot be revoked before they expire, so keep provider token lifetimes short.
- **The development bypass refuses production** (the settings do not load with
  `ENVIRONMENT=production` and `AUTH_DEV_BYPASS=true`, in any process); it is allowed in
  development and test. The compose containers default to production, so a local `.env` needs
  `ENVIRONMENT=development` and the bypass, or a credential.
- **Requirements of the data stores:** Redis for the queue, shared limits and the feed;
  PostgreSQL with pgvector (Neon works, the role must be allowed to create the extension, or an
  owner enables it once); the vector column is fixed at 768 dimensions.
- **No Redis in CI.** The queue and the feed are tested with fakeredis and in-memory fakes; the
  real Redis path (RQ workers, pub/sub) is not exercised by the automated suite; phase 7 found
  the stream-cleanup leak above only by running against a real Redis and uvicorn. The compose
  check in phase 9 started a real Redis and worker but did not run matching (no embedding key).
- **Scoring is not tuned.** The matching thresholds are reasoned starting points, and search has
  no labelled queries yet (about 100 pairs are needed before tuning). The end-to-end test uses
  fake embeddings, whose cosines mean little, so it asserts the hard filters, not fit.
- **Embedding and extraction use a free tier.** Quotas are small; Google may use free-tier
  inputs to improve its models, which is why Remote OK postings are excluded.
